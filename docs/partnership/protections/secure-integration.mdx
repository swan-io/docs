# Secure your integration

When you build an integration that uses Swan services, you are responsible for protecting your integration, your users, and their data.

This page describes common security practices to implement when building and operating your Swan integration. These guidelines are not exhaustive. Implement additional controls and procedures that are appropriate for your architecture, technology, and risk profile.

> **Important**
>
> In the event of fraud, if evidence shows that the your security measures did not follow Swan’s recommendations, you will be liable for reimbursing your user for the resulting fraud.

Visit [Swan’s Trust Center](https://trust.swan.io/) for more information about how Swan protects you, your users, and Swan accounts.

## Protect your integration

### Protect API credentials and private keys

Protect the client ID and client secret that you use to access Swan services. You must also protect any private keys or equivalent credentials used by your integration.

Production secrets must be stored only in an approved, server-side secret-management solution. Do not embed them in browser or mobile applications, source code repositories, logs, tickets, or chat messages.

You must:

- Restrict access to credentials using the principle of least privilege.
- Maintain an inventory of active credentials.
- Replace client secrets immediately after suspected compromise.
- Remove credentials that are no longer required.

### Secure webhook processing

Configure a webhook secret and verify the `x-swan-secret` HTTP header on every Swan webhook request before processing it.

You must:

- Reject requests with a missing or incorrect secret.
- Record processed event identifiers to prevent duplicate processing.
- Apply idempotent handling to state-changing actions.
- Account for at-least-once delivery and out-of-order notifications.
- Retrieve relevant details through the authenticated Swan API or Dashboard when needed.

Do not treat a webhook as the sole source of sensitive information.

### Protect OAuth access and refresh tokens

Swan uses OAuth 2.0 and Bearer authentication. Treat user access tokens, project access tokens, and refresh tokens as sensitive credentials.

You must:

- Store tokens in an appropriate, protected server-side system.
- Store tokens at the correct user or project level.
- Never expose tokens in URLs, logs, or untrusted client-side storage.
- Use user access tokens only for operations that require them, particularly sensitive operations.
- Use project access tokens for server-to-server authentication and non-sensitive operations.
- Use only exact, pre-approved redirect URIs configured in the Swan Dashboard.
- Query Swan’s API to confirm the outcome of sensitive consent flows.

Swan user and project access tokens are valid for one hour.

User refresh tokens are single-use. Store each refresh token securely and replace it with the newly issued token after a refresh.

### Protect your API endpoints and integration flows

Protect your own endpoints as well as your calls to the Swan API.

You must:

- Implement server-side rate limiting.
- Set request-size limits.
- Monitor abnormal API use.
- Use Swan idempotency controls for state-changing operations where supported.
- Use only pre-approved redirect URIs.
- Use current TLS.
- Avoid sending sensitive data in URLs.

## Protect user access

### Enforce a strong password policy

If you use passwords to authenticate users, implement controls that protect against brute-force attacks, credential stuffing, and password disclosure.

Your password policy must include:

- A minimum password length of 12 characters.
- Support for long passphrases.
- Screening of new passwords against known-compromised-password lists.
- Support for password managers and password paste functionality.
- Secure password generation when passwords are generated by your system.
- A password change after first use or reset when the password was generated by your system.
- Rate limiting, progressive delays, and monitoring after repeated invalid authentication attempts.
- Account lockouts designed to avoid creating a denial-of-service risk.
- Password reset or rotation after suspected compromise, credential exposure, or a high-risk account-recovery event.
- Storage using a modern adaptive password hash with a unique salt, such as Argon2id or bcrypt.
- Transmission only over current TLS.

Do not require routine periodic password changes solely because a certain amount of time has passed.

Prioritize password length, uniqueness, and resistance to known-compromised credentials over mandatory composition rules.

### Use multi-factor authentication

Even when strong passwords are used, attackers can obtain user credentials through account-takeover attacks.

You must implement multi-factor authentication for access to interfaces where users can:

- View an account balance.
- View transactions.
- Initiate payments.
- Manage beneficiaries.
- Manage memberships.

Prefer phishing-resistant methods such as FIDO2 or WebAuthn security keys and passkeys. Authenticator-app codes may be used as a fallback.

Swan handles multi-factor authentication for account operations through its [Consent mechanisms](https://docs.swan.io/topics/users/consent/#sensitive). You must implement your own authentication mechanism for sensitive operations handled through your systems and applications.

Multi-factor authentication is not required for cardholder-only access when the only sensitive data displayed is the card number or physical card PIN. These values are protected by Swan’s Consent mechanisms.

### Protect user sessions

Implement controls to protect sessions against session prediction, session fixation, and session hijacking.

You must:

- Set an idle timeout and a separate absolute session lifetime.
- Generate session IDs using a cryptographically secure random number generator.
- Regenerate session IDs after authentication, password reset, and privilege changes.
- Configure cookies with `Secure`, `HttpOnly`, and an appropriate `SameSite` attribute.
- Use `SameSite=Lax` as the default.
- Use `SameSite=Strict` where your application flows allow it.
- Use session fingerprinting or device binding where proportionate to the risk.
- Invalidate sessions after a password reset or suspected account compromise.

You must enforce a five-minute idle timeout when users can access or perform any of the following operations:

- View an account balance.
- View transactions.
- Initiate payments.
- Manage cards.
- Manage beneficiaries.
- Manage memberships.

You may refresh session tokens while the page remains open, provided that the session timeout is enforced when the user is no longer actively using the interface.

## Build secure applications

Implement a secure development lifecycle for systems and applications that handle Swan services, account holder data, or sensitive operations.

Your development lifecycle must include:

- Security requirements.
- Peer review for security-sensitive changes.
- Dependency management.
- Security testing proportionate to the risk.

Your applications must also implement the following controls:

- Validate input on the server using allowlists and type, length, and range checks.
- Use parameterized queries or equivalent safe data-access patterns to prevent injection.
- Use context-appropriate output encoding.
- Use a restrictive Content Security Policy to reduce cross-site scripting risks.
- Protect state-changing browser requests against cross-site request forgery.
- Check authorization on every sensitive server-side action.
- Do not rely on client-side checks alone for authorization.
- Restrict outbound requests to prevent server-side request forgery, including requests to internal services and cloud metadata endpoints.
- Use safe serialization and deserialization practices.
- Do not process untrusted serialized objects with unsafe deserializers.
- Use secure error handling that does not expose sensitive information.

## Protect sensitive data

Protect account holder data stored in your systems and applications.

Implement controls appropriate to your architecture and the sensitivity of the data, including:

- Data segregation mechanisms.
- Network access controls that prevent direct database access from untrusted networks.
- Logical access controls that prevent access by unauthorized users.
- Encryption of sensitive data before storage.
- Automated purge mechanisms when stored data exceeds its maximum retention period.
- Truncation or masking of sensitive data in logs and cache files.

Avoid collecting and storing account data unless it is strictly necessary.

Whenever possible, store object IDs instead of sensitive object values. For example, store `CardID` rather than card numbers.

Where account data must be retained in your systems and applications, encrypt it before storage.

## Separate Sandbox and Live environments

Pre-production environments, including development, testing, and UAT environments, are usually less secure than production environments.

Use Swan’s [Sandbox environment](https://docs.swan.io/topics/get-started/choose-integration/) for development and testing. Maintain proper separation between your Sandbox and Live environments.

You must implement controls that prevent the leakage of Live data into pre-production environments and prevent pre-production environments from accessing Live resources.

These controls may include:

- Network or logical access controls that segregate resources processing Live data from resources processing Sandbox data.
- Separate credentials and secrets for each environment.
- Access-management procedures that separate responsibilities between pre-production and production environments.
- Access restrictions that limit Live access to authorized personnel only.

You must not use Live data during development or testing.

## Patch and harden your systems

Protect your systems and applications against software vulnerabilities and insecure configuration.

### Manage software vulnerabilities

You must:

- Deploy system patches regularly.
- Avoid deprecated or unsupported software.
- Avoid vulnerable application dependencies.
- Update application dependencies as part of the development lifecycle.
- Use vulnerability scanners or perform intrusion testing to identify software vulnerabilities.

Swan highly recommends that you mitigate:

- Critical vulnerabilities within 30 days.
- Non-critical vulnerabilities within 90 days.

Vulnerability prioritization must consider more than severity alone. Where available, use the current version of CVSS and consider:

- Active exploitation, including vulnerabilities listed in the CISA Known Exploited Vulnerabilities catalog.
- Exploit likelihood, including EPSS where relevant.
- Internet exposure.
- Asset criticality.
- The availability of mitigations.

Actively exploited or externally exposed critical vulnerabilities should receive accelerated remediation.

### Use secure configuration

Define hardening standards for your systems and applications. Implement change-management and configuration-management procedures. Use configuration scanners or perform intrusion testing to identify insecure configurations.

Your hardening standards should include:

- Removing or disabling default accounts, passwords, keys, and authentication credentials.
- Configuring network rule sets and access-control lists with a deny-all default policy.
- Disabling unnecessary services, protocols, daemons, and functions.
- Disabling insecure protocols such as Telnet, rlogin, and FTP.
- Enforcing strong authentication mechanisms.
- Enforcing authorization controls.
- Maintaining audit trails.
- Encrypting data at rest.
- Encrypting data in transit, including through the use of TLS.
- Using strong cryptographic algorithms, cipher suites, and modes of operation.
- Protecting systems against malware.

## Detect and respond to security events

Implement procedures to detect, analyze, and handle security events affecting your systems or applications.

You must implement controls appropriate to your architecture and risk profile, including:

- Security monitoring mechanisms such as a SIEM.
- A SOC, CERT, or CSIRT provider, or an equivalent internal function.
- Formal incident-response roles and responsibilities.
- Identification of regulatory requirements that apply to incident response.
- Documented security incident-response procedures.
- IT forensic procedures.

Notify Swan promptly about any security incident that could affect:

- Swan credentials.
- Swan APIs or services.
- Account holder data.
- Swan account holders.

If you discover a potential vulnerability in Swan’s APIs or services, follow the [vulnerability reporting process](https://docs.swan.io/partnership/protections/report-vulnerability/).

## Assess and treat security risks

Implement procedures to ensure that appropriate controls are in place to protect your organization, premises, staff, systems, and applications.

Your risk-management process should include:

- Identifying the assets that need protection.
- Defining a methodology to evaluate security risks.
- Assessing security risks periodically.
- Maintaining a risk-assessment matrix.
- Implementing internal control procedures.
- Monitoring security advisories from technology providers and relevant security communities.

## Maintain security awareness, supplier assurance, and resilience

Maintain governance processes that support the secure operation and continuity of systems handling Swan services, account holder data, or sensitive operations.

These processes must include:

- Periodic security-awareness training for relevant staff, including phishing and credential-protection awareness.
- Risk-based security assessment and oversight of third parties and suppliers that can access sensitive data, credentials, or production systems.
- Tested backup, business-continuity, and disaster-recovery arrangements proportionate to the criticality of the service.
- Procedures to notify Swan promptly of a security incident that could affect Swan credentials, APIs, services, account holder data, or account holders.
